# 合力 · LiftTogether

> 救护车到达之前的搬运方案生成器 —— Swift Student Challenge 参赛作品

一句话：**救护车到之前，怎么把人从屋里挪到能上车的地方。**

## 一、真实问题

院前急救的黄金时间就堵在这十几分钟里，而事故大多发生在**农村自建房**：
三层楼、窄楼梯、瓷砖地面、院门外的泥坡与土路。

现场卡住的从来不是「要不要救」，而是三件非常具体的事：

1. **不知道怎么搬**：老人被"背"起来，脊柱损伤加重或髋部骨折二次损伤。
2. **不知道要几个人**：一个人硬抬，两个人抬反方向，结果比不抬更糟。
3. **不知道哪条路能走**：侧门只有 8 米，但那是 18% 的泥坡；正门要走 22 米缓坡。
   现场的人往往**选了更短的那条**。

## 二、作品思路（对标获奖共性）

| 获奖共性 | 本作品的对应设计 |
|---|---|
| 从具体的人的真实痛点出发 | 站在自家门口打 120 的那些家属与邻居 |
| 多技术串联形成叙事 | 伤情禁忌规则 → 地形评分 → 分工编排 → 坡度剖面可视化 → 一键分享给赶来的帮手 |
| 端上、离线 | 急救时没有信号也必须能用；所有规则内置 |
| 无障碍设计 | 极简三问（什么情况 / 几个人 / 哪条路），大按钮，禁忌用红色独立成块 |
| 交互巧思 | **只显示最安全的那条路，并把被排除的条数告诉用户** |

### 最关键的一个设计

**不是找最短的路，而是找「伤情允许的最短的路」。**

同一条窄楼梯，对「轻伤能走」是捷径，对「疑似脊柱伤」是**绝对不能走**；
同一段泥坡，对轻伤无所谓，对危重伤情是二次伤害来源。
所以 RouteScorer.score() 会返回 nil——不是打个低分，而是**直接否决**。

## 四、诚实边界

- **这不是医疗建议**。它处理的是「搬运方式」，不是「诊断」。
- 伤情由现场的人凭观察选择，所以每一种伤情都配了「绝对不要」清单。
- 没有安全路径时，App 的答案是**先别动患者**，而不是勉强给一个方案。
- 人手不够时，第一句话就是「先别硬抬，先去叫人、先清通道」。

## 五、下一步

1. 接入 Core Motion：用手机本身量出这段路的坡度与台阶，不再靠人填。
2. 接入 MapKit 离线路线 + 高程数据，自动生成候选路段。
3. 语音播报：现场手忙脚乱时，方案能读出来最有用。
4. 与急救调度中心打通，把伤情与预计搬运时间提前告诉救护车。

### v2（本轮）：现场没人有时间读字

竞品（Red Cross First Aid、各种急救手册）都是**给人安静阅读的知识型产品**——
而急救现场恰恰没有安静、没有时间、没有闲人。这一版把方案变成可以"听"的：

1. **免看模式**：完整朗读方案，或只念最要紧的三句（人不够 → 别抬；
   怎么做第一句；禁忌第一句）。语速 0.45 倍，为现场噪音而放慢。
2. **搬运计时**：从开始搬到抬上车用了多久，本来没人记得住；
   而"6 分钟"对医生判断失血与休克有直接价值，一句报告交给家属带去医院。
3. 测试 14 → 21 个（新增免看播报首句、禁忌必须念出、计时与报告）。
